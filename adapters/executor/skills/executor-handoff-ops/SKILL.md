# 外部执行体 handoff 操作细则（按需加载）

本 skill 是 `rules/executor-handoff.md` 的操作层。常驻规则只保留触发条件与硬禁止，判定表和 prompt 模板在这里。调用形态与退出码见 `refs/executor-contract.md`；调用示例：

```bash
aicj-worker --cd <worktree 绝对路径> --tier high "<prompt>"
```

## 一、并行派工决策门禁（按任务依赖图，不按模块数量）

### 1. 先拆任务单元，再过六项门禁

任务单元必须有独立目标、明确写集和独立验证方式；"一个工程 / 模块 / Controller"本身不算任务单元。两个**编码**任务单元仅在六项全部通过时允许并行：

| 门禁 | 通过标准 | 不通过时 |
|------|----------|----------|
| 契约冻结 | 字段、接口、状态、错误码、DDL 归属已明确 | 先串行冻结契约 |
| 依赖独立 | B 不需要等待 A 的代码结果才能开始 | 按依赖顺序串行 |
| 写集互斥 | 不改同一文件、共享 DTO、父构建文件、公共 SQL | 指定单一 owner 或串行 |
| 验证独立 | 每单元有自己的编译 / 单测 / 验收命令 | 合成一个 handoff |
| 状态可控 | 不同时占同端口或修改同一 DB / 缓存 / 消息队列状态 | 编码可并行，环境验证串行 |
| 粒度足够 | 每单元独立满足派外部执行体的门槛（预计工具轮数足够、值得付启动成本） | 合并批处理，不为微改另启执行体 |

任一项不通过，不得靠"涉及多个模块"强行并行；改为串行，或"先冻结公共上游 → 再并行下游"的两阶段执行。纯只读分析不检查写集和运行状态，但问题域仍须相互独立。

### 2. 任务单元写成票据

多单元任务派工前，先把单元写成票据，再对**前沿**（阻塞项全部完成的票据）过六项门禁。

- **切法**：每张票是一条纵向打通的最小链路（入口 → 业务 → 数据 → 测试），完成后能独立验证；大小以一个新开上下文能做完为准。需要预重构的，单独开一张票。
- **宽重构**（改列名、改共享类型这类牵连全仓的机械改动）走 expand-contract：先 expand（新旧写法并存）→ 再按包分批迁移（每批一张票，都被 expand 阻塞）→ 最后 contract（删除旧写法，被所有迁移批次阻塞）。
- **AFK / HITL**：契约已冻结、可直接派的标 AFK；需要看图、消歧或由用户做选择的标 HITL，主会话解决后改标 AFK 再派。
- 票据里不写具体代码（代码很快过时）；只有原型产出的、比文字更精确的决策（状态机、schema）可截取关键片段。

```markdown
# <序号>: <票据标题>

**交付行为:** 从使用者角度描述这张票打通的端到端行为
**被阻塞于:** <序号>… 或 无
**执行:** AFK | HITL
**写集:** 预计修改的模块 / 包

- [ ] 验收条件（可判定）
```

### 3. 并行层选择

| 任务内容 | 选择 | 约束 |
|----------|------|------|
| 多工程 / 多仓库，跨方契约已冻结且各自可验收 | 多工程并行 | 每仓一个 worktree + 一个顶层外部执行体 |
| 单工程内多个平级模块，公共上游不变 | 单工程多模块并行 | 每模块域一个独立 worktree |
| 单工程有公共模块要改 | 两阶段 | 先串行公共契约并形成基点，再并行下游 |
| 同一行为链（入口 → 业务 → 数据）或写集重叠 | 单执行体串行 | 不因跨层 / 跨文件误判为独立任务 |
| 共享完整业务上下文的多个独立只读问题 | 主会话原生子代理 | 外部执行体内部不得再派子代理 |

每个顶层执行体都在自己 `--cd` 指定的 worktree 里独立执行，互不共享 cwd。

### 4. 禁止无界嵌套并行

- 默认一次只启用一个主要并行层：多个顶层外部执行体，彼此互不依赖。
- 外部执行体内部一律不得再派子代理（claude 引擎由 `aicj-worker` 以 `--disallowedTools Agent` 禁止；codex 引擎靠 prompt 末尾的固定约束），防止"外部进程数 × 内部子代理数"的乘法膨胀。
- 顶层并发数受 worktree 并行上限约束，不得为并行绕过登记流程。
- 并发任务 prompt 必须写明：目标、已冻结契约与基点、允许与禁止修改的路径、独立验证命令、返回内容。
- 全部回报后由主会话分别审 diff，按依赖顺序集成，再跑一次聚合编译；服务启动和共享基础设施联调默认串行。

### 5. 快速判例

| 场景 | 判定 |
|------|------|
| 前后端分仓，API 字段已冻结 | 多工程并行 |
| 前端要等后端临时决定返回字段 | 先冻结契约，再并行 |
| 公共模块要改，下游两个模块依赖它 | 公共模块串行完成，下游再并行 |
| 同一接口的入口 / 业务 / 数据三层 | 单执行体串行 |
| 三个模块分别做只读影响分析 | 主会话原生子代理并行 |

## 二、返工输入契约（fix-forward）

已有失败证据要交外部执行体修复时，输入需求与新功能不同，用新写代码的边界清单会让返工变成猜谜。微改动由主会话直接修。

### 必带六项（缺任一不得派工）

| # | 项 | 要求 | 不这么做的后果 |
|---|---|---|---|
| 1 | 失败事实 | 用例 / 测试 ID + 完整 actual vs expected 原文，不转述。actual 若是通用兜底文案（"系统异常""操作失败"之类不含异常信息的提示），必须附真实堆栈或异常类名；拿不到就先去拿（日志、复现抓取、加日志），禁止自行列候选根因让执行体"复现区分" | 执行体修的是你的理解，不是真实现象 |
| 2 | 证据路径 | 证据文件、日志行号、数据查询与结果 | 无法自行复核，只能信你 |
| 3 | 最小复现 | 可直接执行的命令或步骤 | 每轮都要重新搭现场 |
| 4 | 已排除的假设 | "已验过不是 X、不是 Y，依据是 Z" | 执行体重走你已走过的死路 |
| 5 | 禁改范围 | 明确不许动断言 / 测试预期 / 用配置绕过；不许扩大改动面 | 出现"改到绿"：测试变宽而缺陷还在 |
| 6 | 根因判据 | 必须能反向证伪：恢复旧实现，该测试应重新失败 | 改的是症状，下一轮同一处再炸 |

### 批处理

同一轮发现的多个失败一次性交，不"改一个看一个"；执行体每次派工都要付首轮上下文成本，逐条派会按失败数相乘。仅当某个失败阻塞其他失败的定位时才拆轮。

### 返工 prompt 末尾固定追加

```
这是返工任务，不是新功能：
- 先复现上面的失败，确认你看到的现象与 actual 一致，再动手
- 不得修改断言、测试预期或用配置绕过让它变绿
- 修完必须反向证伪：恢复旧实现，该测试应重新失败；把两次结果都返回
- 只改与根因直接相关的范围，扩大改动面前先说明理由
- 已排除的假设不要重走；有新证据推翻它时，先说出证据
```

## 三、测试交接细则

派测试类任务前加载本节（编写 / 维护 / 执行 unit、contract、integration、e2e 资产，或做 UI 验证）。

### 三阶段（固定顺序）

1. **主会话设计 + 数据准备**：冻结行为预期、归属层级、目标环境 / 版本、执行步骤与工具、成功判定、证据要求；同时备好可直接执行的数据（账号、业务主键、前置状态、数据来源、清理方式）。handoff 中禁止留下"执行时再找 / 再问用户要数据"的占位项。
2. **外部执行体实施 + 执行 + 采证**：按冻结方案编写或维护测试资产，使用已备数据完整执行，返回原始结果（命令、退出码、业务断言、必要日志 / 截图）。数据因环境漂移失效时，返回精确缺口和证据，不猜数据、不篡改业务状态。
3. **主会话审查 + 裁决**：检查实现质量、步骤完整性和证据强度，再按冻结预期裁决 PASS / FAIL / BLOCKED。仅在证据不足或高风险点才针对性抽查，不默认重跑已完整执行的套件。

### 执行体职责

- 编写业务代码与按冻结方案编写 / 维护测试资产。
- 使用预先准备的数据执行分配的自动化测试，采集原始证据。
- 在 worktree 内编译并完整运行新增 / 关联测试。
- 返回：实际改动文件、逐项执行结果、命令与退出码、证据位置、已知风险与数据缺口；不代替主会话作最终裁决。
- 声称"已做变异 / 造红验证"时，附变异前后的 diff 输出。

### 主会话职责（不可委托）

- 测试设计、数据准备、证据强度审查、PASS / FAIL / BLOCKED 裁决。
- diff 自审：逻辑正确、副作用（事务·缓存·锁·线程·日志）、异常路径（空值·空集·超时·并发）、周边集成、注释与解释性文字是否多余。编译通过不等于审查通过。
- 不通过放宽断言、跳过测试、跳过测试的构建参数制造"通过"。

### 按归属层实施并执行

| 归属层 | 实施 / 执行 | 主会话复核 |
|------|------------|------------|
| unit | 必写 + 必执行 | 读断言和结果，判断是否覆盖 spec |
| contract | 必写 + 必执行，不塞进 unit | 核对状态码 / 错误码的真实断言 |
| integration | 必写 + 必执行，用真实依赖 | 核对真依赖、数据与落库断言 |
| e2e | 按归属表必写 + 必执行 | 核对版本、首尾状态、完整步骤与原始证据 |
| manual | 不伪装成自动化；可自动步骤仍执行，需人步骤交回 | 核对人工证据并裁决 |

测试 handoff prompt 末尾固定追加：

```
按主会话已冻结的测试方案实施并执行:
- 各层测试分到对应层,该写的写完并实际运行,不混塞、不只写不跑
- 只使用 handoff 中已准备的数据与账号;数据失效时返回精确缺口和证据,禁止猜值或直接改业务状态造前置
- 每个测试名描述具体行为,断言验业务结果,不只断言 mock 被调用
- 返回命令、退出码、业务断言和必要日志/截图
- 只报告原始结果与风险,最终 PASS / FAIL / BLOCKED 由主会话裁决
```

### 批处理要求

- 同一验证载体的多个探针写成一个测试类的多个用例，不要一条用例一个类（每个类都要付一次完整上下文冷启动）。
- 同类用例合并成一次 handoff，执行与证据也按批次一次返回。
- 测试夹具只实现主会话已冻结的数据方案；只新增数据并在事务内回滚，禁止更新业务状态字段造前置。

### 代码审查单元

以"仓库 + 同一 worktree 当前分支 + 固定分叉点"标识的最终可合并 change-set 为审查单位。同一批次的多个 finding 一次汇总、一次返工、统一复审；修复后默认只对修复文件及直接调用链做增量复审，契约或核心设计实质变化时才重新完整审查。
