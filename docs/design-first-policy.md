# Design First Policy v1.0

本文件定义编码前设计完整性门槛。目标是防止 Agent 在需求尚未形成整体设计时直接进入单功能实现，导致模块跑偏、改错位置或后续重构。

设计不是长流程门禁。小任务可以用轻量设计清单，复杂任务必须形成可追溯设计产物。

## 触发规则

必须先补设计再编码：

1. 新项目、完整模块、跨页面/跨接口/跨表需求。
2. 二开项目中涉及既有模块行为、接口契约、表结构、权限、数据隔离、事务、缓存、异步、文件或外部系统。
3. 用户目标从一个系统方向切换到另一个方向。
4. 同一需求已经出现第二轮返工或补丁震荡。
5. Agent 无法明确本次改动属于哪个模块、哪些文件、哪些接口、哪些表。

可压缩为轻量清单：

1. 单文件文案、注释、样式或无行为配置。
2. 明确的小 bug，影响面已由现有代码和测试证明。
3. 用户只要求分析或 Review，不要求实现。

## 新项目设计要求

新项目或完整系统开发前，至少明确：

1. 宏观模块：系统边界、一级模块、核心角色、主流程、导航或菜单结构。
2. 微观模块：每个核心模块的页面/API/Service/Mapper/表/状态/权限/测试入口。
3. 领域模型：实体、值对象、枚举、命令、查询视图和不变量。
4. 数据设计：主表、关系、数据隔离字段、审计字段、幂等键和索引风险。
5. 集成边界：外部系统、文件、消息、定时任务、缓存和失败处理。
6. 验证设计：验收标准如何映射到单元、集成、API、SQL、回归或人工验收。

新项目不能直接从某个页面或某个 CRUD 开始编码，除非已经说明该页面在宏观模块中的位置和上下游影响。

## 二开项目设计要求

存量项目二开、维护或改造前，至少明确：

1. 既有能力：现有模块、入口、接口、表、配置、任务和复用点。
2. 影响范围：新增、修改、复用、废弃的 Controller、Service、Mapper、表、页面、权限、缓存、任务和外部调用。
3. 兼容边界：老数据、老接口、老页面、历史状态、迁移脚本和回滚方式。
4. 风险点：事务、数据隔离、权限、幂等、并发、性能、日志和安全。
5. 不改范围：明确哪些模块不能动、哪些历史问题不在本次解决。
6. 验证入口：用真实开发/测试数据证明修改位置正确，避免只验证新写代码。

二开项目不能只根据需求文本新建一套平行实现。必须先证明目标位置与既有代码路径一致，或说明为什么需要新路径。

## 编码前门槛

进入实现前必须能回答：

1. 本次属于新项目、完整模块、二开改造、小修还是纯文档。
2. 是否已完成宏观设计、微观设计或影响设计。
3. 本次会改哪些模块，明确不改哪些模块。
4. 类型模型、设计简报、架构评审、实施计划和测试计划是否互相追溯。
5. 如果设计不完整，是否先补设计而不是先写代码。
