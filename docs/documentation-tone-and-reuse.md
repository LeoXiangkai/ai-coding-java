# Documentation Tone And Reuse v1.1

本文件定义工具组件文档的表达规范，适用于 `ai-coding-java` 以及后续类似 AI Coding 工具组件。

目标：新组件会吸收外部项目、已有框架或 skill 的有效机制，但文档不能把“没有照搬的内容”写成反向能力缺失。首页要表达能力、边界和取舍，不制造负面观感。

## 首页表达

README、入口页、能力状态页优先使用正向表达：

1. `已落地`：已经可用的能力。
2. `边界清晰`：由项目、运行时或外部平台负责的事项。
3. `后续增强`：已识别但暂不做的增强方向。
4. `范围外`：明确不属于本组件职责的事项。

首页避免使用：

1. `不支持：...`
2. `不负责：...`
3. `不能：...`
4. `不会：...`
5. `无：...`

这些词容易让组件看起来像能力不足。若必须说明边界，写成“由谁负责”或“范围外”。

## 外部经验转化

吸收外部项目、开源 skill、已有框架时，文档必须回答：

1. 转化了什么机制。
2. 为什么适合当前组件。
3. 落到哪个文档、模板或脚本。
4. 是否改变默认流程。
5. 哪些内容明确不照搬，以及原因。

推荐写法：

```text
吸收：需求 checklist 作为复杂需求可选澄清工具。
落地：templates/requirements-checklist-template.md。
流程影响：小任务不启用，复杂需求按需启用。
边界：完整 CLI 和重门禁由外部工具负责，当前组件不绑定。
```

避免写法：

```text
不支持完整 CLI。
不支持采集平台。
不支持强门禁。
```

## 能力矩阵状态词

推荐状态：

| 状态 | 用途 |
|---|---|
| 已落地 | 当前可直接使用 |
| 部分落地 | 有基础能力，但还需要人工补充 |
| 范围外 | 明确不是本组件职责 |
| 后续增强 | 合理但暂不做 |

避免把以下词作为能力矩阵状态：

1. `不支持` -> `范围外` / `由 X 负责`
2. `不负责` -> `边界：由 X 负责`
3. `不能` -> `当前不作为默认能力`
4. `不会` -> `暂不引入` / `后续增强`

## 自动检查

组件内运行：

```bash
python3 scripts/docs_tone_check.py
```

检查重点：

1. README 不出现反向能力清单。
2. 能力状态块使用 `已落地`、`边界清晰`、`后续增强`。
3. `docs/project-harness.md` 的能力矩阵不使用 `不支持` 作为状态。
4. 机制分析文档不把未照搬内容写成首页式负向能力缺失。

该检查是文档质量门禁，不影响业务代码开发。
