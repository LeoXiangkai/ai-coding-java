# TDD Policy v1.0

本文件定义 ai-coding-java 的测试先行分级策略。目标不是把所有任务都变成严格 TDD，而是在高风险业务点上阻止 Agent 先写实现、后补验证。

严格 TDD 技能、RED/GREEN/REFACTOR 执行细节由 Codex、Claude Code 或 OMX 等全局运行时负责；本文件负责项目侧判断：什么时候必须启用，什么时候只需要测试计划和交付证据。

## 分级

| Level | 名称 | 适用场景 | 要求 | 交付证据 |
|---|---|---|---|---|
| L0 | 不启用 TDD | 文档、注释、样式、小配置、无行为变化整理 | 可跳过测试先行，但仍需说明验证方式 | 基础检查或人工确认 |
| L1 | 测试计划先行 | 普通 CRUD、低风险页面、低风险接口 | 开发前明确验收标准、测试层级和验证命令 | test-plan 或交付报告中的验证映射 |
| L2 | 测试优先 | Service 业务规则、Mapper SQL、多表事务、状态流转、库存/金额/权限/幂等 | 实现前先补 focused test、集成测试或可复现回归用例；若无法先写测试，必须说明替代验证 | focused test / integration test / regression evidence |
| L3 | 严格 TDD | 核心算法、线上 bug、库存扣减、金额计算、权限隔离、数据隔离、重复提交、并发保护 | 必须先产生 RED 证据，再最小实现 GREEN，重构后保持全绿 | RED 失败证据、GREEN 通过证据、最终验证命令 |

## 触发规则

默认按风险选择最低可接受级别：

1. 无行为变化：L0。
2. 一般行为变化：至少 L1。
3. 影响核心业务状态、数据库写入、事务、权限、金额、库存、幂等或数据隔离：至少 L2。
4. 修复已出现的 bug，尤其是线上 bug、复发 bug、数据错误：至少 L2；能稳定复现时优先 L3。
5. 用户显式要求 TDD、测试先行、RED/GREEN/REFACTOR：L3，除非任务属于 L0 且说明原因。
6. 无测试框架或环境暂不可用时，不得把 L2/L3 降级为“已验证”；必须记录阻塞、替代验证和剩余风险。

## 执行口径

### L1 测试计划先行

1. 写清验收标准。
2. 把验收标准映射到 unit、integration、API/curl、SQL、regression、manual。
3. 实现后必须提供可复查证据。

### L2 测试优先

1. 优先补业务断言测试，而不是 mock 调用次数测试。
2. bugfix 先补能复现问题的回归测试，再修复。
3. 多表写优先用 SpringBootTest / Mapper 集成测试证明事务和 SQL 语义。
4. 如果只能用 curl、ego、SQL 或人工验收替代，交付报告必须说明为什么不能自动化。

### L3 严格 TDD

1. RED：先写最小失败测试，并确认失败原因是目标行为缺失。
2. GREEN：只写足够让测试通过的实现。
3. REFACTOR：在测试保持通过的前提下清理命名、重复和结构。
4. 交付报告必须写出 RED 和 GREEN 的命令或证据。

## 不适合强制 L3 的场景

1. 纯文档、纯样式、纯配置整理。
2. 主要验证手段是浏览器交互或外部系统，且无法稳定自动化。
3. 存量项目缺少测试基础设施，当前任务目标不是建设测试框架。
4. 生成代码或一次性原型，但必须在交付报告中标明范围。

## 与其他文件的关系

1. `docs/testing-workflow.md` 定义需求测试、代码测试和交付证据链路。
2. `docs/verification-matrix.md` 定义最低验证强度。
3. `docs/rd-integrated-workflow.md` 定义复杂需求的需求、类型、架构、计划和测试产物。
4. 全局运行时的 TDD skill 可以执行 L3 的具体 RED/GREEN/REFACTOR；ai-coding-java 不复制全局 skill 逻辑。
