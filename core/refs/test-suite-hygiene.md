# 测试套件维护规则

适用于已经积累了一定数量自动化测试的项目（unit / contract / integration / e2e）。

## 为什么存在

自动化测试套件最大的敌人不是"覆盖率不够"，而是"红得没人信"。一旦出现 5+ 条偶发失败的测试，整个套件的信任度就会崩盘——开发者会默认"红了重跑就好"，真 bug 也会被忽略。本规则规定怎么处理这种"信任度腐烂"。

## 一、flaky test 判定与隔离

### 判定条件（任一满足即算 flaky）

- **同一测试**在不修改代码情况下，连续 3 次跑里有 2 次以上结果不一致（绿/红混合）
- 同一测试在不同时段（白天/夜间）跑结果不一致
- 测试本身没改但 CI 里偶发红，重跑就过

### 隔离动作（发现即做）

1. 加 `@Disabled` 或 `@Tag("quarantine")` 注解（JUnit 5）
2. 文件头加注释，写清：
   - 隔离日期
   - 偶发失败的现象
   - 临时责任人（谁加进 quarantine 谁负责）
3. **不删测试源码**，便于后续修复

### 不允许的处理

- ❌ 加 `@Retry` 反复重试盖过去
- ❌ 改宽断言（`assertEquals` 变 `assertNotNull`）让它"稳定通过"
- ❌ 加 `Thread.sleep` 押注时序

理由：这三种处理是把"测试不稳定"伪装成"测试通过"，污染整个套件信任度。

## 二、quarantine 退出机制

quarantine 不是"垃圾桶"，是"待修复区"：

| 时间 | 动作 |
|------|------|
| 进 quarantine ≤ 2 周 | 责任人定位真实原因（数据 / 时序 / 并发 / 测试本身写错），修完移出 |
| 进 quarantine > 2 周仍未修 | **直接删除测试源码**，不留半成品 |
| 真 bug 触发的 flaky | 必须修业务代码 + 测试代码，再回归通过才能移出 |

**Why**：留太久不修的 quarantine = 永远不会修。删掉比"挂着"更诚实，至少不再消耗后人的精力。

## 三、测试退役

下列情况测试应**直接删除**，不进 quarantine：

| 条件 | 处理 |
|------|------|
| 被测代码已删除 | 同步删测试 |
| 被测方法已 `@Deprecated` | 同步删测试或迁移到替代方法 |
| 行为已通过其他层覆盖（如原 unit 已被 integration 覆盖且重叠） | 删 unit 保留 integration |
| 测试 6 个月以上从未失败过 + 对应代码也没改过 | 候选删除（不强制，但可清理） |

**判定原则**：测试是为了在改代码时给信号，没失败过的稳定路径不需要永久守护。

## 四、新测试加入门禁

新测试加入主套件前必过：

1. **本机连续跑 3 次全绿**（防止一加进去就 flaky）
2. **断言不空**（不是 `assertNotNull` 占位）
3. **测试名描述 spec 行为**（不是 `test1()`）
4. **属于明确的归属层**（unit/contract/integration/e2e 任一，不是含混）
5. **已落在该层的宿主里，且已登记索引**（见 §四点一）

不过门禁的测试不进主套件，进 quarantine 或退回作者修复。

## 四点一、资产宿主唯一且须显式声明

「写完了」不等于「交付了」。测试资产**必须落在该类型资产声明的宿主里**，且宿主只有一个。

| 约束 | 含义 |
|---|---|
| **宿主唯一** | 同一份资产不得在两处各存一份可运行副本。两份必然漂移，而漂移时没人知道哪份是权威 |
| **宿主须声明** | 项目要在自己的 `.claude/CLAUDE.md`「测试基础设施映射」里写明每层资产的宿主位置；没声明 = 下一个人只能猜 |
| **脱离业务仓的宿主要自带三样** | ① 版本控制 ② 依赖清单（锁定版本） ③ 一行可复制的 entrypoint。缺任一，资产就是"存着但跑不起来" |
| **登记后才算交付** | 落盘 + 在项目资产索引里有行，两步都做完。只做第一步 = 下次验证时找不到它 |

**为什么把「登记」也放进门禁**：索引不是文档工作，它是**检索入口**。没有入口的资产等于不存在——
下一轮验证会重新手搓一份，而重搓的版本与上一版细节往往对不上，证据从此不可比。

**典型失败形态**：e2e spec 写完、实跑、失败证据都已归档，用例台账里也写了目标位置——唯独没 `git add`，也没进资产索引。
它们在临时 worktree 里以未跟踪状态滞留；收口检查只在主检出跑 `git status`，**兄弟 worktree 里的未跟踪文件根本看不见**。
门禁本身没被违反，是它看的地方不对。

**已知不覆盖**：本条只管资产落位与可检索，不管资产**质量**（那是 §八）或**是否该存在**（那是 SDD 归属表）。

## 四点二、检索先行：动手做测试前必须先查资产索引（机械门禁）

§四点一 管「资产落在哪、登记没登记」，本节管**用之前先查**。适用于**任何**测试工作——
不只是批次验证，也包括临时验证、探索、手点、起浏览器、写一次性脚本。

**硬顺序**：查索引 → 判 `reuse` / `update` / `add` → 才动手。反过来就是重复造资产。

| | 动作 |
|---|---|
| **检索第一站** | 项目声明的资产索引（位置写在项目「测试基础设施映射」里），**不是磁盘、不是记忆** |
| **机械入口** | 项目若提供索引检索命令（按业务关键词 / 接口片段检索、漂移体检），优先用它 |
| **检索证据** | 逐字写「查资产索引 `<模块>` 行 → 命中 / 未命中」 |
| **命中** | 走 `reuse` / `update`；禁止新增同一路由·角色·动作·预期的脚本 |
| **未命中** | 仅当索引与磁盘**无漂移**时才可据此判 `add`；有漂移先补登记 |

两条易错点：

1. **接口反查索引的「未命中」是未知，不是无覆盖**（它只含跑过的用例）。拿它判 `add`
   会重复造一份已存在的资产。
2. **索引漏登记 = 检索假阴性**。索引是权威事实源，所以漏登记要当场补、不是绕开它直扫磁盘；
   检索时顺带做漂移体检，存在未登记项时不得给出干净的「未命中」结论。

**Why**：只写在批次验证流程里的检索条款，会被日常的「帮我验证一下 X」「探索下这个页面」完全绕过；
「查索引 → 未命中 → 新建」这条路径上会持续积累假阴性。条款不缺，缺的是触发器——项目有条件时应配机械提示或拦截。

## 五、与 SDD 测试归属表的关系

- 行为单元从归属表拆出 → Dev 写对应层测试 → 跑通进主套件
- 主套件中的测试腐烂 → 按本规则隔离 / 退役
- 退役后行为未被新测试覆盖 → 必须更新归属表，标"该行为单元当前由 manual 兜底"或"无覆盖"，不能让代码裸奔

## 六、何时审计

- 每个里程碑收口时
- 当主套件红率 > 5% 时（不是改对了就是套件腐烂）
- 季度 audit

审计动作：

```bash
# 跑一遍套件，记录每条用例的通过/失败
# 找出连续 3 次跑里偶发失败的，标 quarantine
# 检查 quarantine 目录里超 2 周的，直接删
```

## 七、不在本规则范围

- 性能测试的稳定性（指标波动是正常的，不算 flaky）
- 测试数据准备失败（属于环境问题，不是测试本身腐烂）
- 单条测试本次失败（要先确认是真 bug，不是先标 flaky）

## 八、AI 写测试 review 清单（复核 AI 产出测试时必走）

读 AI（Claude / 任何代码生成器）新增测试时，逐项过下面清单，任一不通过就要求重写或自己补：

1. **断言验业务结果，不是验 mock 被调用**
   - ❌ `verify(service).save(any())` 单独存在
   - ✅ 断言 DB 状态变更 / 返回值字段 / 异常类型
2. **测试方法名描述 spec 行为**
   - ❌ `test1()` / `testSave()`
   - ✅ `submitWithDuplicateIdCard_shouldReturn409()`
3. **过度 mock 自检**
   - ❌ mock 了被测对象本身，或 mock 了实际要验的 SQL
   - ✅ 只 mock 外部依赖（外部核验接口、人脸 API、第三方 HTTP）
4. **异常路径覆盖**
   - 必填校验 / 权限拒绝 / 外部失败 / 状态非法 至少各有一条对应单元
5. **断言不空**
   - 没有 `assertNotNull` 后什么都不验的"空壳测试"
6. **layer 层级正确**
   - 看 import：有 `MockMvc` 必属 contract；有 `@SpringBootTest` 必属 integration；不允许 contract / integration 测试退化成纯 Mockito unit
7. **注释不写废话**（判据见 `rules/context-engineering.md §产出侧`：删掉它，读者会做错什么？）
   - ❌ 复述测试方法名已说明的行为、复述被测代码的步骤、给 `arrange/act/assert` 逐行加说明
   - ✅ 只写非显然的：前置数据从哪来（真实反推 / 造数脚本）、时序或清理约束、为什么断言这个值而不是另一个、为什么必须 mock 掉这个依赖

清单不通过的处理：

- 简单问题（命名 / 断言空）→ 自己改
- 结构性问题（层级错 / 缺异常路径）→ 退回让 AI 重写，带 review 结论

## 九、测试结果完整性红线（反 smoke 降级 / blocked 滥用 / 状态造假）

测试结果只有"真跑出来的"才算数。下列七类都是**伪造通过 / 掩盖未跑**，硬禁止：

1. **blocked 滥用**：凡能写出 SQL / API 方案就**必须执行**。"破坏性 / 耗时 / 会污染状态"都不是标 blocked 的理由——识别后能做却没做 = lazy blocked。
2. **静默降级 pass**：smoke ≠ passed。`passed` 必须执行完整 steps + expected 全绿。要放宽判定标准**必须先问用户**，不许自行降级。
3. **批量 blocked 是红旗**：连续 3+ 条 blocked 或整批 blocked，立即停下反问"能造数 / 切角色 / 补 UI 路径吗"。相似 actual/evidence 的批量 blocked 就是 smoke 降级换皮。
4. **改状态字段的边界（有条件放宽）**：为跨过**本批次不验证**的前置环节，允许直接把业务状态字段（`audit_status` / `verification_flag` / `signed_status` 等）更新到所需状态，避免验证被与本批缺陷无关的流程环节卡住。**红线仍在**：禁止对**本批次正在验证的那个行为本身**直接改状态——例如本批要验的正是"审核通过后是否自动流转到下一节点"，就不能直接把状态改成"下一节点待审"再断言它通过，那是拿结论当前提的自证造假。
   - **流程顺序**：同一批次内属于同一条业务链的多个用例必须按流程顺序先后验证；前一环节已由本批用例真实跑通后，后一环节才可以用"直接置状态"跳过它，不能先跳到后面环节再回头补前面的。
   - **留痕**：直接置状态仍须完整走 §十 六步协议（快照 / 定界 / 验写点 / 变更并验原始结果 / 业务侧回读 / 恢复或冻结），并额外记录：改了哪张表哪几行、从什么状态改到什么状态、为哪条用例服务、为什么该状态不属于本批验证对象。
   - 核验类（外部真实性核验，如身份证查户籍、人脸活体）仍应优先用真实数据反推；确无法反推、又不属于"本批不验证的前置环节"时，只能 `blocked:data`。
   - 与 `refs/design-doc-principles.md §4.8 测试数据策略` 呼应。

   **Why**：原条款一刀切禁止改状态字段，会让验证卡在与本批缺陷无关的前置环节上，逼人反复走产品流程把无关环节走一遍才能到达要验证的那一步。裁决保留的是"不能拿结论当前提"这条判别力红线——直接改的必须是本批不关心的旁支状态，不能是正在验证的目标状态本身；流程顺序约束防止用"先跳过再回填"掏空这条红线。
5. **steps 必须完整执行**：`evidence-chain` / `duplicate-of` / `reuse` 都不算"跑过"，每条 step 必须有实际 API/UI 证据；复用证据必须**显式声明**覆盖到哪条分支。
6. **交付前主动自审 5–10%**：不等用户质疑。actual 雷同 / 过短 / 空壳 actions / 截图复用无 evidence_chain = 可疑信号，回退重跑。
7. **跳过 / 零执行 / 排除档位必须显性化**：未真正执行的层在结论里只能写 `Not-tested`；部分通过不得写成通过或打 ✅（若已安装 verify-probe 可选插件，开工前先跑探测，汇报时附其报告）。典型漏洞：`@EnabledIfEnvironmentVariable` 集成测试默认整类 Skipped 仍 BUILD SUCCESS（用 `-D` 传开关同样被跳过）；e2e 默认 `--grep-invert @needs-data` 不跑核心数据用例。

**Why**：套件里一旦出现伪造的"通过"，下次同链路真出 bug 时谁也不信测试，整个套件失去守护意义。破坏的是**信任**——比单条用例写错更严重，且不可逆。

**How to apply**：每条用例落 `passed` 前自问"这是真跑出来的，还是 blocked/复用/降级凑的？"；批量结果里 blocked 占比异常先停手反问，不闷头交付。

## 十、共享测试环境状态变更协议

测试或联调要修改共享环境的配置、开关、缓存、第三方账号绑定或公共夹具时，固定执行下面六步。

**适用范围含业务数据的增、删、改**：为了准备测试前置，**通过产品自身的接口 / UI 流程**在共享库上新建活动与申请、推进审批、开闸门、驳回、撤回、作废或删除自己的样本，是正当手段，不因"库是共享的"而一律禁止——但必须走完下面六步。这与 §九 第 4 条一致：产品按业务规则改是首选正道；确需绕开流程直接改业务状态字段时，只能用于 §九 第 4 条放宽的范围（跨过本批次不验证的前置环节），且要遵守其流程顺序与留痕要求——对本批次正在验证的行为本身直接改状态，仍是硬红线。

六步：

1. **快照**：变更前读取并记录原值、目标环境、时间和读取证据；不能凭记忆填写“原值”。
2. **定界**：列出受影响服务、缓存键/配置项/数据行及并行使用者；同一共享状态的写操作串行执行。
3. **验写点**：确认目标确实可写且属于预期环境，例如核对 DB/schema、配置中心环境，或用 `ROLE/INFO replication` 确认 Redis 写到 primary；只读副本和来源不明的连接禁止试写碰运气。
4. **变更并验原始结果**：保留命令退出码和原始返回，核对影响行数、`DEL/SET` 返回或平台响应是否符合预期。禁止吞掉 stderr、用 `|| true` 掩盖失败，或未验结果先打印“已修改/已清缓存”。
5. **业务侧回读**：从真实消费方（接口、应用日志、配置查询或最终存储）确认新状态已经生效；只看写命令成功不算完成。
6. **恢复或冻结**：在 teardown/`finally` 中恢复第 1 步快照并再次回读；若任务明确要求保留新状态，则记录最终值、保留原因、影响范围与责任人，显式冻结后才可不恢复。

任一步失败都必须停止依赖该状态的后续用例，并报告“变更失败”或“恢复失败”；清理失败必须让套件失败，不能静默跳过。该协议不授权超出 §九第 4 条边界的状态伪造：直接置状态只能用于该条放宽的范围（跨过本批次不验证的前置环节），对本批次正在验证的行为本身直接改状态仍属造假，§九第 4 条边界仍优先。

**Why**：共享开关未恢复会污染后续批次；写到只读副本却吞掉错误会制造“已生效”的假证据。两类问题都破坏整套环境验证的可信度，必须把快照、原始结果、业务回读和恢复变成同一条闭环。

## 十一、Why 这条规则单独成立

- 测试套件维护是长期工程，不放进 `refs/design-doc-principles.md` 会被淹没
- flaky test 的处理动作和"写测试"是不同问题域
- 自驱循环依赖测试套件可信，套件腐烂会让整个自动化失去意义
