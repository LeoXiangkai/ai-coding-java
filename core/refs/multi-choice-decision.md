# 多选一决策规则

## 反模式（禁止）

来回折返式决策：

```
用户："按 X 判重"
Claude：好的改成 X（写进文档）
用户："要不要加 Y"
Claude：加 Y（又改）
用户："但 Z 场景怎么办"
Claude：回退 Y 重新加 W（第三次改）
```

每一轮都是一次思考 + 文档修改 + Token 浪费，且文档腐烂（每次改完要同步 SQL / Redis key / 测试点）。

## 正确模式（一次决策）

发现方案有 2 个以上合理候选时，**立即停止实施**，先列候选表给用户。

**表格模板**：

| 方案 | 做法 | 业务含义（举 2-3 个典型场景的行为差异） | 影响（技术/数据/用户） |
|------|------|-------------------------------------------|-----------------------|
| A | ... | 场景1: ... / 场景2: ... / 场景3: ... | ... |
| B | ... | 场景1: ... / 场景2: ... / 场景3: ... | ... |
| C | ... | 场景1: ... / 场景2: ... / 场景3: ... | ... |

然后**问一个明确问题**：
- "按你的业务预期，A/B/C 哪个对？"
- 或 "你能描述一下 XX 场景的预期行为吗？"

用户一次回复定下，后续实施无反复。

## 触发时机

实施过程中出现下列信号时，**立即暂停**，列候选表：

- 思考方案时出现"嗯但也可以这样"的分叉
- 对业务规则的一处判定有多种合理解读
- 技术实现有 2 条以上路径且代价/取舍不同
- 用户的描述里有歧义短语（"跟 X 一起"、"按 X"、"支持 Y"）
- 遇到"要不要加 X"、"是否允许 Y"类问题

## 写候选表的要求

1. **重点写"业务含义"**，不是"技术实现"（用户关心业务）
2. 每候选附 **2-3 个典型场景的行为差异**（比较"向 A 申请 / 同时向 B 申请 / 失败后重提"等具体场景）
3. 候选表发给用户前，自问："如果我是 PM，这个表够我做决策吗？"不够就补
4. **决策做完后冻结进设计文档**，后续实施不再反刍
5. 如果你明显知道某个候选是错的（违反已有约束），不要列上；只列真正可选的

## Why

1. 业务规则的合理性取决于业务上下文，Claude 不是 PM，没法替用户判断
2. 反复修改会让文档腐烂，且让用户反复回忆上下文
3. 典型复盘：判重维度改了 3 次（证件号 → 证件号+机构 → 证件号+当前+目标 → 回退证件号单维度），第一次就列候选能省 2 轮往返

## 例外

- 只有一个合理方案时，直接实施，不必造假候选
- 用户已明确选定时，不再列候选；但实施中若发现用户选定的方案会破坏已有约束，要停下重新问，不要硬上

## 远程异步决策：无人值守时

上面讲的是「人在终端前」的同步决策——列候选表、用户当场选。**人不在终端前时这条路是死的**：
交互式提问弹在没人看的终端里等于永久阻塞。

此时改走**远程决策通道（可选，若已配置）**：把问题、候选项与受阻原因推送到用户可及的消息渠道，等待回复。未配置时回落普通交互提问，不阻断。

### 何时必须走它

1. 判定为无人值守时的**任何需用户拍板的决策点**
2. 任务因**缺资料 / 环境不通 / 权限不足 / 外部依赖不可用**而无法推进时

日常人在场的轻量澄清继续用交互提问，别为小事走远程通道。

### 回复处理协议

| 回复 | 动作 |
|---|---|
| 选中「停止任务」 | 立即停手，汇报已完成部分；**不许自作主张换方案继续** |
| 选中其它选项 | 按该选项继续 |
| 直接给出资料 | 拿资料原文继续执行 |
| 超时无人回复 | **停任务**并说明卡在哪。超时**不是**默认同意 |
| 通道出错 | 报错并停，不重试刷屏 |

### 反面清单

- 不许猜缺失的资料、硬编造内容
- 不许跳过决策点自己拍板
- 不许把超时当默认同意
- **同一决策点只发一次**，超时就停，不许连发刷屏

**Why**：本规则原本只解决「人在场时别来回折返」，但无人值守下「人在场」这个前提不成立。
远程通道是同一条纪律的**异步版**——决策权仍归用户，只是把问答通道从终端换成消息渠道。
