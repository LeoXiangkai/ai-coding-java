# 工程权衡决策框架

适用于技术选型、架构决策、规则设计、工具开发等任何"多个方案都说得通"的场景。

## 当前阶段优先级（默认值，项目或用户可覆盖）

**高效 > 成本 > 性能**

阶段语义：决策正确率仍是最大痛点（错误成本高，用户来回纠错的代价远超开发成本），token 成本是第二痛点——常驻上下文是每轮的乘数，长会话被整体放大。性能（hook 延迟、查询速度）退居第三：几十毫秒的延迟用户感知不到，而每轮多读几万 token 是真实成本。

落到具体决策时：

| 出现冲突时 | 倾向 |
|----------|------|
| 高效 vs 成本 | 优先高效（该写的规则还是要写，别为省 token 让模型反复犯错） |
| **成本 vs 性能** | **优先成本（宁可多 30ms 延迟，也要少注入几 k token）** |
| 高效 vs 性能 | 优先高效 |

**对常驻上下文的具体含义**：

- 每轮常驻的东西（`rules/`、skill description、MCP 工具 schema、hook 注入）按 **token × 轮数** 记账，不按行数
- 新增常驻内容前先问：**它每轮都必须在吗？** 不是 → 进 `refs/` 或正文，靠触发器按需加载
- 判断"要不要为省 token 牺牲点什么"时：**牺牲延迟可以，牺牲决策正确率不行**。典型应用——压缩 skill description 时删"能力清单/决策树"（对路由零贡献）可以，删触发词不行

**何时调整**：常驻上下文回落到可接受水位后，若"用户来回纠错"重新成为主要痛点，回到「高效 > 性能 > 成本」；若出现工具卡死 / 延迟明显影响操作，升入「性能 > 高效 > 成本」。

## 核心三角

任何工程决策落在下面三角的某个点上：

```
        成本(开发/维护)
            ▲
           ╱ ╲
          ╱   ╲
         ╱ 现实 ╲
        ╱  sweet ╲
       ╱  spot   ╲
      ╱──────────╲
   性能(运行)   高效(决策正确率/用户体验)
```

没有同时拉满三角的方案。每次选择本质是**问哪个角最重要**，放弃另两个的极致。

## 阶段判断（决定哪个角最痛）

| 阶段 | 最痛的角 | 典型决策倾向 |
|------|---------|------------|
| **早期** | 成本 | 用最便宜的方案先跑通，不预优化(jsonl 而非 SQLite,bash 而非 Python 服务) |
| **中期** | 高效（决策正确率）| 错误成本高，宁可冗余检查、强制自省、规则前置 |
| **后期** | 性能 | 用户量大、调用频次高，毫秒计较，开始引入索引/缓存/异步 |

**关键纪律**：

- **判断当前阶段，按当前阶段的痛点决策**
- **不为下一阶段的痛先付出成本**（过度工程的根源）
- **不假装当前是后期**（早期就上 SQLite/微服务/分布式锁是典型陷阱）

## 决策自检（做技术选择前必跑）

1. **现阶段哪个角最痛？** 用上表对照
2. **当前方案优化的是最痛的角吗？** 不是 → 重新评估
3. **放弃的两个角，我能承受多久？** 越久越说明判断对
4. **下个阶段的痛点出现前，这个方案能撑住吗？** 能 → 不要再优化
5. **能用最便宜的手段达到 80% 效果吗？** 能 → 别追 100%

## 度量纪律：优化/立项前先测瓶颈，别凭推断

上面「决策自检」第 1 问是**现阶段哪个角最痛**——这问题**没测过就答不了**。凭直觉认定瓶颈，是本框架最常见的失效方式。三条：

1. **别凭单次异常立项**：单次出现 + 其他 run 干净 = **执行方差**，不是系统性缺陷。据此立项 = 为不存在的问题做优化。
2. **测瓶颈要按成分拆**：总耗时只告诉你「慢」，不告诉你「慢在哪」。先拆出各成分占比，再决定优化谁——优化了占 21% 的那部分，天花板就是 21%。
3. **噪声 > 信号时，端到端尺量不出来**：此时「没测到提速」**≠**「改动无效」，而是**仪器分辨率不够**。换**能隔离信号的尺**（组件级计时 / microbenchmark / 纯试算基准），别用端到端秒表下「无效」结论。判收益看**是稳定移带还是带内波动**，不看单次数字。

**Why（不同技术栈复现过同一课）**：

- **Java 计算引擎 / 共享测试机**：排查「为什么压不到 0」连错 2 次因，都是凭推断没做对比实验；正解 = 纯试算基准隔离链路噪声 + 控制变量 + 看分布形状。2% 的改动配 ±20% 噪声的共享机秒表永远量不出，要本地 microbenchmark / profiler。
- **Python 本地 LLM Agent**：「规划器」的立项证据（工具重复调用）实为单次执行方差，基线跑 3 次全干净 → 纯亏 33% 耗时零收益；「并发工具执行」估「工具 I/O 占大头」实测只占 21%（79% 是 LLM 推理），端到端被噪声淹没看不出，隔离测组件才看到真 2 倍。

**How to apply**：立项优化前先自问「**这个瓶颈是测出来的还是推出来的？**」——推的就先去测，通常 2 分钟的事，省的是一整轮白改。已有可回归的 eval / benchmark 时，**改动前后各跑一次**并按成分看，别只看总数。

## 反模式

| 反模式 | 表现 | 修正 |
|--------|------|------|
| **预先优化下一阶段** | 单人工具上 SQLite / 分布式 / 微服务 | 用 jsonl + tail，需要时再升级 |
| **凭推断认瓶颈** | "这里肯定慢/这里会重复" 就动手改 | 先测（见 §度量纪律）；推的不算数 |
| **拿噪声>信号的尺量** | 端到端秒表量 sub-noise 的改动，量不到就说"无效" | 换隔离信号的尺；"没测到"≠"无效" |
| **假装三角能拉满** | "既要、又要、还要" | 强制选最重要的角，承认放弃 |
| **不分阶段** | 早期 MVP 就追性能 | 早期成本第一，性能放后 |
| **沉默的复杂度** | 隐藏在自动化里的复杂依赖 | 显式 wrapper 比隐式 PATH 劫持好 |
| **被工程美感绑架** | "应该有索引、应该用 ORM、应该上中间件" | 问"现阶段够用吗"，够用就停 |

## Why（本规则的真实案例）

**case 1：jsonl 经验库**

- 选项：jsonl（每行 JSON，append-only）vs SQLite（带索引）
- 三角：jsonl 是「成本第一」点，SQLite 是「性能第一」点
- 当前阶段：单人工具、行数 < 5000、查询 < 50ms
- **选 jsonl**：性能够用 + 成本最低 + git diff 友好（高效）
- **何时改 SQLite**：行数 > 50000 且查询 > 200ms（后期痛点出现时）

**case 2：git index.lock 解法**

- 选项：wrapper（显式）/ PATH 劫持（透明）/ 系统 git 替换（侵入）
- 三角：wrapper 是「成本第一」点，PATH 是「高效第一」点，替换是「性能第一」点
- 当前阶段：单仓库偶发撞车
- **选 wrapper**：30 行代码、不破坏 IDE 的复杂 PATH、可显式调试
- **放弃的角**：每次调用多一层 fork（5ms，可接受）、需要记得用 wrapper（用 rule + hook 强制）

**case 3：经验库 dedup 窗口**

- 选项：永不重复 / 永远只留 1 条 / 24h 窗口
- 三角：永不重复=性能差成本低，只留 1 条=高效差(丢高频信号)，24h=平衡点
- **选 24h dedup**：兼顾文件增速 + 保留高频信号 + 实现成本可控

## 元规则

本规则本身也遵循三角：

- 写在 refs/ 而非常驻规则（避免每次会话注入完整框架）
- 不抽象出"通用决策引擎"（过度工程）
- 一份文件，< 150 行，方便修订
