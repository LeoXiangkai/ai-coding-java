# 需求澄清

## 职责与输入

把原始需求变成完整、明确、可供测试设计使用的需求文档。必须保留原始需求语义；任何补充或修正都要等待用户确认。需要原始需求和项目声明的业务知识库路径。按知识库自身的索引结构读取 `_index.md`、维度索引、命中模块概览、强相关详情与场景流程；设定加载预算，超出时分批读取。

本 skill 不产出任务清单、测试用例、代码或执行报告。产出的“影响范围”是下游测试设计的权威输入。

## 五步流程

1. 通读原始材料，提取模块、功能、角色、操作和数据对象，写出不超过 30 字的需求主旨。
2. 知识库路由：先读 L1 索引，再按关键词读 L2 概览，最后只读强相关 L3 详情及跨模块场景。知识库不存在或稀薄时明确标注判断可能不完整，不假装拥有业务事实。
3. 做四维分析：
   - **完整性**：触发/前置、输入边界、正向与异常、角色权限、状态转换、数据影响、多端展现是否齐全。
   - **合理性**：对照业务规则、状态机和依赖识别冲突，给出依据位置。
   - **影响范围**：分为直接模块、相关模块、数据依赖；只按知识库证据和需求内容推导。
   - **补充建议**：为每个缺项、冲突和影响点给出可执行的澄清问题。
4. 把分析结果逐条交用户选择：接受、修改、忽略或暂不处理。未确认内容保持 TODO，不自行合并。
5. 用户确认后输出 `<原需求名>_澄清版.md`，包含需求主旨、完整流程、异常、角色、数据、多端行为、澄清说明、三级影响范围和知识库追溯索引。写文件前先展示草稿。

## 输出约束

每个判断标注依据位置，例如 `domain/<module>.md:Rnn` 或 `scenarios/<flow>.md`；找不到依据时标“待确认”。跨端需求逐端写清行为。知识库不足时提示补齐知识库，但仍可基于已提供需求输出带边界的分析。默认不改写原始需求，也不把推测写成已确认规则。
