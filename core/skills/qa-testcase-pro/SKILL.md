# 测试用例设计与导出

## 输入和边界

主体是经 `req-analysis` 澄清的完整需求；项目知识库仅用于理解业务背景和影响范围，不替代新需求。先读取项目声明的知识库索引，再按关键词加载模块和场景，控制加载预算。知识库缺失时明确提示可能不全，不编造业务事实，也不读取历史用例目录作为主体。

一次性用例设计使用本 skill；没有具体新需求、要长期维护系统资产时使用 `qa-baseline`。

## 阶段 0：配置

未指定时使用：项目名从需求提取；编号前缀 `TC`；起始编号 1；分组层级 3；输出到项目声明的输出目录。不重复询问已提供的配置。

## 阶段 1：测试点

按优先级梳理三层：

1. 核心业务逻辑：端到端主流程、业务规则、异常流程。
2. 数据交互：输入等价类与边界、多条件组合、联动、计算、权限和过滤。
3. 界面交互：布局、文案、按钮、加载、空数据和易用性。

主用例覆盖需求的正向、反向、边界和异常；另按需求澄清文档的“影响范围”（直接模块、相关模块、数据依赖）补充关联回归用例。每条关联用例记录来源类型和具体依据。安全、兼容、性能只在触发矩阵命中时生成，触发判断可引用 `qa-baseline/references/trigger-matrix.md`。

输出测试点 Markdown 表格（L1/L2/L3、编号、测试点、类别、优先级），去重后暂停等待用户审阅。知识库规则驱动时，逐条覆盖有效业务规则、枚举、校验、屏蔽、边界、异常和访问控制规则，并追加覆盖率及未覆盖原因。

## 阶段 2：详细用例与导出

用户确认后，将每个测试点展开为 13 个字段，构造 JSON 并运行 `scripts/generate_xlsx.py`。缺少 `openpyxl` 时脚本必须退出码 2，提示“需要 openpyxl；请在项目环境自行安装，或改用 Markdown/CSV 降级输出”；组件不安装依赖。

### 13 列

`id`、`test_item`、`priority`、`requirement_id`、`title`、`preconditions`、`steps`、`expected`、`test_data`、`is_reverse`、`type`、`automation_type`、`ai_generated`。分组列为 `group_l1` 到 `group_l5`，按需启用并自动合并相邻相同值。

`type` 使用 `Functional`、`E2E-Positive`、`E2E-Negative`、`Boundary`、`Negative`、`UI/Interaction`、`Compatibility`、`Performance`、`Security` 或 `Regression-Related`；优先级使用 P1–P4。预期结果必须是可观察、可复现、可判定的业务结果。

## 交付检查

确认编号唯一、前置条件真实、步骤完整、每个断言有对应业务产物、反向用例标记正确、关联来源可追溯。导出成功后报告文件路径、用例总数、分组层级、优先级分布和专项触发情况。
