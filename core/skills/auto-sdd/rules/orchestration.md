# auto-sdd · 任务编排（冷层，按需加载）

> 主文件只留指针。当要 fan-out 子代理、派工、核实产出时加载本文件。

auto-sdd 不必单 agent 串到底,但**编排得守纪律**。

**四个执行体、各自 lane**(主 agent = 编排中枢,其余受其调度 / 门禁):
- **人** = 门禁·拍板:红线停 / 打磨期 §人工审核闸 / 业务多选决策。
- **主 agent(CC)** = 编排中枢·单点综合:拆活 + 定并行/串行 + 派 subagent/外部执行体 + **独立核实所有产出** + 持账本 + 收口集成;微改(≤5 行)自己改。
- **subagent** = 并行·只读工:事实核查 / 独立 reviewer / 活体对账 / 多 bug 调查 / e2e 回归。
- **外部执行体** = 串行·实现工:业务码 / 单测 / DDL(单写者,见 `rules/executor-handoff.md`);不可用时子代理顶。

下面 6 条是这套分工的执行纪律,每条来自实跑踩坑或权威经验(多代理研究系统实测:编码任务真正可并行的子任务远少于研究任务),不是"感觉该并行"。

1. **默认不为并行而并行(克制阀)**:多代理 token ~15× 单聊。**编码主路保持串行 + ledger note 前传**(见主文件「逐 goal 自驱」),只在下面"该 fan-out"清单命中才拆。

2. **怎么派:首选前台同步并发,后台先验真**。派子代理**首选前台同步 `Agent`**(同一条消息发多个 = 并发,**最稳,本会话已验真跑**)。`run_in_background:true` 本应是自主后台,但**可能被路由进 teammate/mailbox 机制——落 mailbox 就不自执行 spawn prompt、挂 0 token**(本会话实撞:spawn 回执出现 "will receive instructions via mailbox" 即此态)。**用后台前先确认它真在执行;0 进度静止立即回退前台。teammate/mailbox 命名持久体一律不用于自驱派活。** 后台返回带异常签名 + 异常低 token 多半还在重试,**别立即查/测它的产物**(会 race 到中间态)。

3. **该 fan-out(并行只读子代理)** —— 仅 research-shaped、无写冲突:
   - 需求/契约**事实核查**(查口径 / 字段 / 职责归属 / 跨域接口语义)——并行只读调查,别主 agent 串行猜
   - gate-design 的**独立 reviewer**(已在设计门)
   - 多个**互不依赖的 bug 调查**
   - **已固化 e2e 脚本**的回归复测(纯脚本、无探索)

4. **不该 fan-out(串行)** —— 实现型一律串行:
   - **编码 goal 默认串行**:守 executor-handoff 单写者纪律 + 防"既写码又改测试"reward hacking;只有 `Depends=∅` 且**文件边界不相交**的 goal 才可并行,且**绝不并行多个会改重叠文件的实现子代理**
   - 失败相关 / 共享状态 / 互相依赖的活——并行只互相污染

5. **派子代理 prompt 自包含(它不继承你的上下文)**:必含 **objective+scope / constraints(显式"不要改 X")/ boundaries("不要做 Y,那是另一子代理的活")/ 结构化 expected output**;**产物落盘才算数**——结论落 ledger evidence 行 / 产物文件,口头 summary 不算。

6. **产出必独立核实,强度按风险分级**(泛化"执行体声明核实"):🔴 高风险(红线 / live 数据 / 契约 / 安全)→ **派独立 reviewer 全验**(本会话多个 P1 即此抓到);🟠 中(业务逻辑)→ 主会话抽检关键声明 + 跑一遍验收;🟡 低(文案 / 机械改动)→ 直接信 + 抽查(别为低风险烧全验 token)。**任何产出 0% / 前提明显错(找不到目标、答非所问)→ 先疑 prompt 框定错,重新打包重派,别采信也别在坏框定上重试**(实跑:调查子代理因 prompt 没排除编号歧义跑偏,重框后即对)。
