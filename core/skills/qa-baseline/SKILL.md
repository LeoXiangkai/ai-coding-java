# 系统级功能测试基线

## 适用范围

目标项目没有专职测试人员，需要可持续复用的测试资产。首次使用且项目没有 `.qa-baseline/` 时只建立正向基线；目录已存在时按新需求流程补充正向和反向用例。一次性测试用例用 `qa-testcase-pro`，本地构建与接口联调用 `local-verify`。

在项目根目录维护：

```text
.qa-baseline/
  cases.md
  regression/
  business-rules.md
  reports/
```

不要把 `.qa-baseline/` 与其他历史导出目录混用。只保留状态、最后验证时间和关联缺陷等必要字段，不维护无实际用途的组织协作字段。

## 流程

### 首次建立老系统基线

1. 梳理模块、功能和核心流程；规则存疑或文档矛盾时先记入 `business-rules.md`，未确认规则不生成确定性断言。
2. 只写正向用例到 `cases.md`，P0/P1 流程另写可执行回归脚本到 `regression/`。
3. 记录每条用例的执行时间、实际结果、请求响应/日志/截图等证据；没有证据只能标 `BLOCKED`。

### 新需求基线增量

1. 梳理新增、修改、删除功能及完整业务规则。
2. 生成正向用例，并覆盖数据、流程、权限、业务规则、系统异常五类反向场景：空值/非法值/边界、跳步/重复提交/终态再操作、越权、临界冲突、网络/并发/依赖失败。
3. 按 `references/risk-scoring.md` 评分测试深度，按 `references/trigger-matrix.md` 判断安全、兼容、性能专项；不要因改动小而默认跳过。
4. 执行并把证据写入 `reports/<日期>-<需求或系统名>.md`。

### 失败、复测与并入

- 先在报告中判断是代码错还是用例错；说不清时按代码错处理。代码错时按原预期复测失败用例、同流程已通过回归和改动模块单测；只有明确需求改变并记录依据时才改用例。
- 禁止放宽预期、换更容易的数据/账号、改状态为废弃或拆出失败步骤来制造 PASS。
- 验收通过后，把新用例和回归脚本合并进 `.qa-baseline/`；废弃资产标记“废弃”保留记录。
- 合并后使用 `git-commit` 的验证门禁：无其他任务分支合入、来源明确、无冲突/手工改写时跳过重复整套验证；否则仅跑受影响范围的定向回归。用户明确要求全量时再跑全量。

## 证据与结论

状态只用 `PASS / FAIL / BLOCKED / N/A`。不得在共享或生产环境做不可逆操作；敏感数据必须脱敏，不直接改数据库业务状态伪造前置条件。最终按 `references/checklist.md` 判定“通过 / 有条件通过 / 不通过”，并显式列出风险、阻塞项和未覆盖内容。
