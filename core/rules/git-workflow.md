# Git 工作流规则

## 分支命名与推送策略

**命名**以 `refs/git-policy.md` 为唯一权威（`feature/` / `refactor/` / `hotfix/` / `release/` 等斜杠前缀），本文件不复制命名表；
**推送/合并**用本地基线模型（不套 gitflow 的"每分支 push + PR"）。

- **斜杠前缀**,不再用旧的 `feat_`/`fix_` 下划线约定。
- **本地分支一律不 push**:所有本地创建的分支只在本地,默认**合入基线分支**(如 `develop`)。
- **只有基线分支 push origin**:统一由 `develop`(或项目约定的基线)对接远程,不直接 push main/master。
- **测试环境部署来源 = 远端基线分支**:修复未进远端 → 先合入基线并 push 再部署,不推任务/临时分支来部署;流水线配置里的默认分支不可沿用。点「执行」前的确认保留。
- **基线分支名不写进规则/skill/memory**:由项目声明(项目 `AGENTS.md` / `CLAUDE.md` 的「当前基线分支」行),任务分支再以 `git config branch.<task>.baseline` 记录;项目未声明时问一次并写回项目声明,换基线只改那一行。
- worktree 生命周期/登记见 `rules/worktree-management.md`。

## 合并后验证门禁

开发分支应在合并前完成其自身的编译、测试和必要的真实链路验证；合入基线不默认重复执行同一套验证。
由 `git-commit` skill（若已安装）的 worktree 收口流程执行以下判定；未安装时由主会话按下列条件自行判定：

- 任务分叉点到合并前基线 tip 之间没有其他任务分支的合并，且使用受管控的 `--no-ff` 合并、无冲突/手工改写 → 跳过重复回归；
- 期间检测到其他任务分支合入，或发生冲突/手工改写、分叉/合并来源无法可靠判定 → 合并后仅做一次受影响范围的快速定向回归；
- 快速定向回归不是全量测试，用户明确要求全量回归时才执行全量套件；
- 旧分支缺少不可变分叉提交元数据、或历史采用 fast-forward/squash 等非标准合并时，不得静默跳过，按来源不明执行定向回归。

## 产物与提交命名规范

### 不得携带任务身份（文件名 + 提交信息）

**禁止模式**（两处通用）：任务序号 / 阶段编号 / 缺陷 ID / 工单号 / 测试 case 编号，例如 `H4`、`H5`、`R1/R2`、`C01`、`C03`、`TASK-379`、`FIX-20260913-01`、`#5650398`、`batch-02`。这类标识只能存在于任务台账、测试证据、发布批次和外部工单系统。

- **文件名 / 类名**：新建的业务代码、测试、脚本、SQL 和长期文档必须描述**稳定的业务职责或行为**，不把临时任务结构固化进代码库。业务本身定义的稳定编号不受限（数据库迁移版本、正式协议版本、真实业务批次号）——判据是**编号脱离当前研发任务后是否仍有业务或工具语义**。
- **提交信息**：使用 Conventional Commits（`feat` / `fix` / `refactor` / `docs` / `chore` / `test` / `perf`）；subject、body 和 trailer 只描述**改了什么、为什么改、如何验证**。一般英文技术术语允许保留，禁止的是用于追踪研发任务的名称或标识。不照抄历史中的违规提交风格——查看最近提交只用于识别 Conventional Commit 类型与项目语言习惯，与本节冲突时以本节为准。一个提交只做一件事。

**提交前自检**：对 staged 新文件名和待提交 message 搜索上述模式；命中时先判断是否为稳定业务编号，无法说明稳定语义的不得提交，文件名命中时先改为业务语义名。

## 安全
- 提交前检查是否包含敏感信息
- 不 force push 到 main/master
- 不使用 --no-verify 跳过 hooks

## index.lock 撞车

可选：安装 `git-safe`（放入 PATH）后，git 写命令撞上 `index.lock` 时自动退避重试；未安装时按下面的人工步骤处理。
禁止手工 `rm .git/index.lock` 或杀 IDE 进程；确认持续撞车时先用 `lsof <repo>/.git/index.lock` 查持有进程，删 lock 前先 `cp .git/index .git/index.bak`。
