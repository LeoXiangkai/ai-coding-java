# Worktree 管理规则

## 适用边界

- 适用于所有由 Claude Code 主导的项目
- 仅约束 git 仓库内的 worktree 使用方式
- 不替代分支策略,只规定"何时开 worktree、放哪、怎么清理、谁在用"

## 硬约束（常驻）

- **本地分支一律不 push origin**：所有 `feature/` 等本地分支只在本地，默认合入基线分支（如 `develop`）；**只有基线分支对接远程**。
- **主工作区禁止任何仓库文件改动**：文件改动任务中主工作区只做 worktree 列表查看、REGISTRY 维护、最终合并收口。
- **改文件前必须先 `cd .worktrees/<name>`**，严禁默认改主工作区。
- **并行 worktree ≤ 5**，超出先收口再开新的。
- 分支命名唯一权威 = `refs/git-policy.md`（`feature/` / `refactor/` / `hotfix/` / `release/` 斜杠前缀）。

## 何时需要 worktree（以仓库文件写入为边界）

**预计会新增、修改或删除 Git 仓库内文件的任务，必须先创建或复用 worktree。** 包括业务代码、测试、配置、文档、脚本、DDL / SQL 迁移和锁文件；即便只改一个文件或一行配置，也走 worktree 流程。

**不修改仓库文件的任务不创建 worktree。** 典型场景：

- 只读代码分析、影响排查、事实查询
- 直接执行数据库查询 / 数据清理
- 日志查询、接口探测、浏览器验证
- 外部平台操作、部署执行、流水线或环境状态查询

worktree 只隔离文件，不能隔离数据库、Redis、MQ、端口或外部平台状态。对纯环境操作（如测试库数据清理）机械创建 worktree **没有保护作用**——只会多出一个空 worktree 和它的清理步骤。

**动态升级**：任务起初判定为只读或纯环境操作，过程中若发现必须修改仓库文件，须在第一次文件写入前停止当前操作，按本规则创建或复用 worktree 后再继续。

**Why 文件写入不留豁免**：主工作区当前所在分支**不可控**——可能停在上一个里程碑的 `develop_xxx_pX`、上一个未推送的 `feature/yyy`、或某个临时 `feature/zzz`。直接在主工作区改：
- 改动会落到**错的基线**上（本想改 master 的文档，结果落到里程碑分支）
- 污染未推送的并行任务工作区
- 后续 merge 链路不可预测

| 任务类型 | 是否需要 worktree | 生命周期 | 命名前缀(gitflow) |
|---------|------------------|---------|------------------|
| 新模块开发 / 跨模块新功能 | 是 | **长期(完成后保留,供后续复用)** | `feature/` |
| 大重构 / 试验性方案 | 是 | **临时(收口后立即删)** | `refactor/`(试验也可 `feature/`) |
| 修复 bug(开发期) | 是 | **临时(合入基线后立即删)** | `feature/` |
| 分析 / 排查且需要修改仓库文件 | 是 | **临时(产出结论后立即删)** | `feature/` |
| 单文件改动、配置 / 文档调整 | 是 | **临时(合入基线后立即删)** | `feature/` |
| 线上紧急热修 | 是 | **临时(合入基线后立即删)** | `hotfix/`(从当前 `release/` 切,见 `refs/git-policy.md`) |
| 只读分析 / 数据库或外部环境操作 | 否 | — | — |

**关键纪律**:
- "临时"型 worktree **收口后立即** `git worktree remove`,不留 done 态过夜
- "长期"型 worktree **合入基线后保留**,REGISTRY 状态从 `active` → `paused`,后续同范围任务优先复用(走 §"REGISTRY 三步法")
- "保留"不是"永久保留":长期 worktree 若超过 **一个里程碑**没新任务复用 + 已全部合入基线,周期清理时一并回收

## 选择执行位置三步法（按顺序执行）

1. **读 `.worktrees/REGISTRY.md`**
2. **按"模块+范围"字段做语义匹配**：
   - 任务主体落在某 worktree 已声明"范围"内 → **复用**
   - 即便任务会新增跨模块支持文件（如 mq Consumer、common 枚举），只要主体仍在原范围，仍算复用
   - 只有任务主体明确跨越所有已有 worktree 时才新建
3. **复用前**：确认 worktree 工作区 clean；若落后集成分支则 `git merge <integration> --ff-only` 拉齐再开工

**新建 worktree 的前置检查**：写出"为什么已有 worktree 不能满足"的一句话理由；写不出来就说明应该复用。

## 操作细则（按需加载 `refs/worktree-ops.md`）

下列任一命中时**先 Read `refs/worktree-ops.md`**，其中条款约束力与本文件等同，只是改为用时加载：

| 触发器 | 取什么 |
|---|---|
| 要新建 worktree | §基线选择（最新本地提交分支优先）的 5 步算法与 `fork-oid` 元数据记录 |
| 要写 / 更新 REGISTRY | §活跃 worktree 登记 的字段表与状态机（active/paused/merging/done） |
| 要在 worktree 里起服务 / 占端口 | §运行时隔离（同一时刻只允许一个 worktree 启动应用） |
| 走完整改动流程 | §文件改动与审查流程 9 步 |
| 里程碑收口 / 月度清理 | §周期清理 脚本与按类型分流回收 |
| worktree 元数据损坏 / 改错位置 / 分支冲突 | §异常处理 |
| 要用 `isolation: "worktree"` 或 `claude --worktree` | §原生能力配合（绕过 REGISTRY，仅限短生命周期） |
| 目录命名、磁盘卫生、嵌套禁令 | §目录与命名、§卫生约束 |
