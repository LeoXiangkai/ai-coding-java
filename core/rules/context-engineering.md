# 上下文工程规则

## 读取原则

- 先定位目标，再读取内容
- 一次优先只聚焦一个模块或一个问题面
- 沿调用链逐步展开，找到所需信息即停

## 默认搜索顺序

- 改接口：Controller -> Service -> ServiceImpl -> Mapper
- 改查询：Mapper / SQL -> 调用方 Service
- 排查 Bug：报错点 -> 直接调用链 -> 相关配置
- 新增模块：参考一个成熟模块即可，不做横向全量对比

## 大文件处理

- 先 grep 定位方法 / SQL / 关键段落，只读相关片段，不整文件吞入（成本对照见 §成本权衡）

## 自省纪律

若安装了教训闭环适配，历史教训会在工具调用前自动召回、用户纠错会自动沉淀；读到即遵守。

- 写接口文档 / 引用字段值·状态码·字典：必追到源常量（§三段式-2；返回码实例见 §偏差反模式）
- 用户说"不对/错了/应该是"：立即承认偏差，三段式重新核对，并考虑沉淀为教训或规则

**强制原则**：用户纠错过的同类问题**不允许第二次出现**。出现即说明经验没用上，是自省失败而非"巧合"。

## 定位—引用—验证 三段式（结论性陈述前必走）

读代码做结论时，**省 token 不等于偷工**。只 grep 命中一行就下判断是经典偏差源。三段式：

### 1. 定位（grep / glob）

- 带行号 `-n`，看清**命中总数**而非只取第一条
- 不依赖单一关键词，命中过多时换更精确的限定词

### 2. 引用（Read 命中前后 ±20~30 行）

- 不只读命中行 — 必须看清**条件分支、异常路径、注解、import 别名**
- 看到 `XxxConstant.YYY` / `XxxEnum.ZZZ` / 静态导入 → **顺链追到源定义**，不靠命名猜值
- 看到 `@Deprecated` / `@Conditional*` / 注释里的 "TODO" → 警觉，重新评估有效性

### 3. 验证（至少 2 处独立证据）

| 场景 | 必须交叉的证据 |
|------|---------------|
| 字段名/类型 | entity + mapper XML + DDL（三方对齐） |
| 字典/枚举/状态码 | 注释 + 代码字面值 + DDL/字典表（注释滞后是高频雷） |
| 接口返回结构 | Controller + Service 实现 + 工具类常量源（不能停在 `sendSuccess(data)` 表层） |
| 跨模块契约 | 前端调用方 + 后端 VO（两边都看） |
| 业务规则 | 代码 + 测试用例（unit/integration 至少一个真实路径） |
| **stream/filter/findFirst 取值类逻辑** | **必须用真实 DB 数据样本验证至少 1 次**——仅看代码推断结果是危险的，特别字段允许 null 且 DB 实际有 null 时（review 过、编译过、单测可能也过，但生产数据失效） |
| **Java 层 entity 字段比较** | **`XxxConstant.equals(entity.getField())` 前必须先核对两侧类型一致**。ORM 注解决定 entity 字段类型，常量类型由定义决定，不一致时 `equals` 永远 false 但编译过（Integer vs String 是最常见雷） |

**输出标注**：结论必须能说出"证据在 `<file>:<line>` 那段"，否则降级为"推测，待验证"。

### 3.4 改数据写入/计算侧前，先列消费侧（缺陷修复同样适用）

**判据**：改动业务数据的写入、计算或主数据配置前，先回答"这个数据还被谁消费"，沿**数据流**而非调用链查。
消费方出现**判断/匹配 · 权限范围 · 冗余副本**任一语义 → 该改动升 T2，消费方清单写进修复说明的影响面。

- 召回：词表取**DDL 表名 + 列名 + entity 驼峰字段 + 注释含业务词的列**（冗余副本多藏在别的表里），`git grep -i` 宽搜；宁多勿漏
- 候选多时可用语义检索工具辅助分类（可选）；候选少到能直接读完时直接读
- 抽查若干已知答案校准后再信任工具的分类结果

**反模式**：只沿调用关系查（静态调用图对反射、MyBatis XML、动态代理大多解析不了）；关键词区分大小写或只搜实体名（漏 `preXxxName` 类冗余列与 Mapper XML 里的消费方）；把"展示字段"当成只影响展示。

### 3.5 接口/字段/SQL 改动的硬约束（编译过 ≠ 行为对）

改动以下任一类型时，**push 前必须本地起服务 + 真实 DB 数据 curl 一次接口**，否则不算"已验证"：

- 新增 Controller 接口
- 改 VO 字段 / 字段填充逻辑
- 改 Mapper SQL（含 lambda wrapper / xml）
- 修 bug 涉及上述任一

**为什么**：编译/单测/代码 review 都可能放行，但**真实 DB 数据形态**（NULL 多、字段类型与常量错位、JOIN 返回多行、加密字段未解密）只在跑通接口时才暴露。本地自测 5-8 分钟，发布后联调返工 30-60 分钟。

**操作模板**：起服务 → 用真实账号拿登录态 → curl 接口并对照 DB 查询结果核对字段值。

**只有真实 DB 数据才暴露的三类形态**（编译过、单测可写绿、code review 看不出）：
- **类型错位**：`Integer.equals(String)` 恒 false → 查询恒空，报"记录不存在"
- **多行取一**：`.findFirst()` 落在允许 null 的字段上，按插入序拿到 null 那条 → 全链路 null
- **加密字段**：读出密文，解密在调用链别处

### 3.6 Bash 工具 cwd 持久化（写路径前必先 pwd）

Claude Code 的 Bash 工具会**保留上一次 cd 后的 cwd**（跨多次 Bash 调用持久化），但**shell 状态不持久**（变量/函数会重置）。

**典型踩坑**：

- 前一条 `cd app-back && mvn ...` 让 cwd 变成 `.../app-back/`
- 后一条 `git add app-back/app-web/...`（凭印象用相对前缀）→ 实际路径变成 `app-back/app-back/app-web/...` → `No such file`

**强约束**：

任何写路径（add/cp/mv/rm/Read/Write/Edit）前，如果不确定当前 cwd，**必先跑 `pwd` 一行**确认，或用项目根的绝对路径。

| 场景 | 推荐 |
|------|------|
| 长会话有多次 cd | 写路径前先 `pwd` |
| 项目根固定 | 用项目根绝对路径 |
| 单次小操作 | `cd <root> && <cmd>`（用 `&&` 显式声明 cwd） |

**Why**：Bash 工具的 cwd 是隐式状态，最容易被忽略——典型后果是写出 `app-back/app-back/...` 这类重复前缀路径。

### 3.7 Bash 工具可能跑的是 **zsh**，不是 bash（`cmd $ARGS` 不分词）

macOS 默认登录 shell 为 zsh 时，Bash 工具实际由 zsh 执行（`$0` = `/bin/zsh`、`ZSH_VERSION` 已设、`BASH_VERSION` 未设）。
**zsh 默认不对未加引号的参数展开做词分割**（与 bash 相反）：

```sh
A="-x -y"; set -- $A; echo $#     # bash → 2 ; zsh → 1
```

即 `mvn $MVNARGS` 会把整串当成**一个**参数传进去。

| 写法 | 后果 |
|---|---|
| `ARGS="-pl m -am test"; mvn $ARGS` | ❌ 整串成单参数，mvn 瞬间失败 |
| 参数直接内联写在命令行 | ✅ 推荐 |
| `ARGS=(-pl m -am test); mvn $ARGS` | ✅ zsh 数组会展开 |
| `setopt shwordsplit` 后再用 | ✅ 但不如内联直观 |

顺带两个同源 zsh 差异：`*` 无匹配时**报错**`no matches found` 并中止（bash 默认原样传递），
所以 `grep --include=*.java`、`ls app-*/d:` 这类要加引号；报错前缀形如 `(eval):13:`。

**失败形态**：命令秒退、缺预期输出行（如无 `Tests run`），**不报参数错误而伪装成业务失败**。
与 §3.6 同源——工具环境与直觉不符且静默失败。
**判断"实验没跑出结果"时，先排除观测装置本身坏了，再怀疑被测对象。**

## 偏差反模式（自检清单）

写"结论性陈述"前自问，命中任一即回到三段式：

- [ ] 只看 grep 命中行没看周围条件分支 → 可能在错误分支里
- [ ] 看 import 推断功能 → 可能只是残留 import
- [ ] 看一处实现推断 N 处 → 可能横向不一致（多 builder/strategy 差异）
- [ ] 看注释/javadoc 不看代码字面值 → 注释滞后是常态（字典枚举注释与 code 值错位是高频事故）
- [ ] 看 mapper XML 不看 entity → 字段名/类型可能对不上
- [ ] 看 wrapper 不追到常量定义 → 如 `ResultUtils.sendSuccess()` 实际返回的 `code` 可能是 `"success"` 这类字符串常量，而非想当然的 `"0"`/`"200"`
- [ ] 看测试用例推断生产链路 → mock 假数据可能掩盖 MQ/缓存/限流真实路径
- [ ] 看 worktree 当主分支现状 → 可能改动还没 merge

## 成本权衡

精确定位 + 必要扩展，**不是非读全文即只读一行**：

| 错误做法 | 正确做法 |
|---------|---------|
| 全文读近万行 ServiceImpl | grep 定位 → 读命中前后 ±30 行 |
| 只读 grep 命中那 1 行 | 读 ±30 行确认分支语义 |
| 看到 `XxxConstant.YYY` 就猜 | 多花一个 grep 追到字面值 |
| 看到第一处实现就推所有 | grep 出所有匹配，挑 2-3 个差异样本对照 |

多花 1-2 个 grep + 几十行读取 ≪ 结论错了重做的代价。

**Why**：看到 wrapper 方法就按常识推断返回值是高频偏差（实例见 §偏差反模式）。多 1 个 grep 追到源定义，省一次返工修文档。

## 降噪规则

默认降权或跳过：

- `legacy`、`old`、`backup`、`unused`、`temp` 目录或命名
- 大段注释代码
- 明显历史备份文件

## 产出侧：注释与解释文字的留白（写注释 / 文档 / 用例说明前必走）

上面「降噪规则」管**读**（别把噪音读进来），本节管**写**（别把噪音写出去）。判定只有一问：

> **删掉它，读者会做错什么？** 答不出 → 不写。

| 反例 | 为什么是噪音 |
|------|------------|
| 重复调用方 javadoc 的清单（「调用方传什么 query 就应用什么筛选」+ 两行 `<ul>`） | IDE 可查引用 |
| 与上方 javadoc 重复的行内注释（`// 本接口不接受参数，传空 query = 全量`） | 同一句说两遍 |
| 装饰性括注（`（列表页的常规入口）`、`（与列表一致：名称模糊、编号精确）`） | 去掉不损失信息 |
| javadoc 里写 `**加粗**` / 靠 `<p>` 分段撑行数 | javadoc 不渲染 markdown |
| 步骤编号 `// ①②③` | 仅当步骤间有**顺序约束**才值 |
| 自相矛盾的括注（`（本接口已在 Controller 层限制为管理员）` 挂在写着普通用户分支的 javadoc 上） | 比不写更糟：误导 |

**该写的**（都答得出「删了会做错什么」）：

- **why**：非显然的约束 / 踩过的坑 / 取舍理由。例：`// 未指定子单位时不走汇总接口，实测汇总接口只返回首页数据`——删了后人会把取数改回汇总接口，直接漏数据
- **魔数来源**：`int pageSize = 500; // 上游接口限制最大500`
- **跨方法隐式耦合**：`// 数据范围由 applyDataScope 写入`
- **顺序约束**：`// type 在转 VO 后才填充，故须在转换后过滤`
- **防回归**：`blob.type.includes('application/json')` 旁注「后端错误响应带 `;charset=UTF-8`，全等比较恒 false」

**落点**：设计文档自审、编码注释的 diff 自审（`rules/executor-handoff.md` 主会话硬门禁）、测试代码与用例说明的 review 都按本节判定；本节是权威，其他文件只引用不复制。

**Why**：AI 生成文字默认偏长——重复调用方已写过的说明、给自明代码加括注、用加粗与分段撑篇幅。这些注释不提供信息却增加 review 负担，且会随代码改动腐烂成**错误**信息源（呼应上文「注释滞后是常态」）。典型形态：一个新增方法的 javadoc 写到 16 行，其中重复调用方的清单、自相矛盾的括注、javadoc 内的 markdown 加粗全是噪音。

## @Deprecated 类硬禁用

**已被 `@Deprecated` 注解的类/方法,不能作为业务代码的参考,也不能新引用**(降权不够,要禁用)。

判定时机：
- `grep`/`Glob` 找到候选类后,先 `head -30` 看类头是否 `@Deprecated`
- 引用前对类名做一次 `grep -n "@Deprecated" <file>`,若命中,跳过另寻替代
- 字典/枚举类尤其要注意：`@Deprecated` 常意味着 **code↔name 映射的语义已经与现状脱节**

**Why**：`@Deprecated` 意味着语义可能已与现状脱节。最危险的形态是**字典/枚举的 code↔name 映射整体错位**——
枚举语义与业务字典各说各话，用户选 A 落库成 B 的 code、前端按字典渲染回 C，**编译/单测/review 全过，只在生产暴露**。

**How to apply**：
- 引用前:`grep -B 1 "class XxxEnum" <file>` 看类头注解
- 字典/枚举类 deprecated → **新建独立枚举**,不复用
- 若被迫要参考已废弃的类,先读 deprecation 说明,理解"为什么废弃"后再决定能否用

## 微小改动的值链路核查

沿用已有模式做小改动前，先核查新值的获取/传递链路是否语义等价（例如同名字段一处是明文、一处是密文；一处来自登录态、一处来自请求参数）。

## 交互规则

- 优先使用支持选项式确认的交互方式
- 若当前环境不支持选项式确认，用简短直接的问题澄清
- 不为低风险、可逆步骤频繁打断用户
